# 法务迭代三：修复“审查失败 / 0 条可采纳修订”、模型规划检索与并行化

基线：`main@6e57257`。本轮没有变更密钥、会员、存储地域或已有合同数据。

## 复现

样例为用户提供的《口腔AI智能化年度赋能顾问服务合同 法律审核报告（甲方版）》：339 个段落、约 1 万字，其中 41 段含全角空格（U+3000），没有可脱敏实体。
回放方式：模型和检索换成可控桩，其余全部是生产代码。即使模型每条引文逐字准确、复核全部通过：

- 深度审查：汇总阶段的输入超过 12.5 万字符预算，任务以“本步骤上下文超过预算”部分完成，所有修订被标为不可采纳，可采纳 0 条。
- 新增回归测试（340 段）：原实现下，标准审查和深度审查的可采纳修订均为 0。
- CI 实网检索诊断：Bing RSS 没有取得任何可用来源，只能读取写死的 3 个官方网址。

## 根因

1. 汇总调用把全部意见重复放入三次，另附未截断的引用原文，因此超出预算。汇总失败后，`apply_cross_edit_checks(None)` 会把复核已支持的修订全部拦截；标准模式的一致性批次失败时同样如此。
2. 每次调用都重发全部段落，并带偏移量和脱敏区间：1 万字的合同每次约 4 万字符。9 到 15 次模型调用顺序执行。检索逐条规则串行，而且每条规则都重新下载《民法典》整页。
3. 法律意见有三处被吞掉：
   - 理由里一提到合同自身的条号（如“合同第八条”），整条意见就被替换成“待核实”模板。
   - 没有检索到原文的法律意见，分析和修改建议会被清空。
   - 法律意见永远不计入风险统计。
4. 逐字引文校验不容忍空格差异。模型把 U+3000 写成普通空格时，整条意见被丢弃。
5. 合同问答用正则 `第.+?条` 判断法条主张，“第三条”“第一批……条件”都会命中，回答被替换成“材料不足”。
6. 输出上限 8192 token、读超时 150 秒，截断即失败且不重试；模型回复前有一句说明文字也会导致失败。

## 改动

- **并行流水线（标准与深度审查共用）**：
  - 规划调用（交易事实 + 法律检索规划）与各审查组同时开始。
  - 某一组审查完成且检索就绪，就立即对该组做复核。
  - 最后用一次精简调用，只检查各拟议修改能否同时采用。
  - 关键路径约 3 次模型调用，与规则数量无关。
  - 进程内并发由 `LEGAL_MODEL_CONCURRENCY` 控制，默认 6。
  - 断点续跑时只重做失败的组；兼容性检查结果按输入指纹复用。
- **精简输入**：发给模型的段落只保留 id、正文和页码。汇总与兼容性检查只使用意见摘要。回放中单次调用的最大输入由 9.4 万字符降到约 3.6 万字符。
- **失败不再“全有或全无”**：
  - 兼容性检查失败、缺项或结论不确定时，在每条修订上标为“未完成交叉核对”，已被复核支持的修订仍可采纳。
  - 只有明确报告冲突时才拦截一键采纳。
  - 实际选择的修改组合在导出前仍须通过“组合核验 + 人工确认”。
- **模型规划检索（不再写死）**：
  - 规划调用按合同内容列出需查证的法律问题、法律全称、确有把握的条号，以及通用检索词。
  - 确定性闸门拒绝含脱敏代称、金额、长数字、链接，或与合同原文有 10 字重合的检索词。
  - 检索并行执行，总时限 60 秒，官方页面缓存 1 小时。
  - 检索范围为 `site:gov.cn` 与沪深北交易所；准入白名单增加证监会、交易所、国资委、外汇局、卫健委、工信部、人社部、知识产权局、版权局、金融监管总局。
  - 搜索结果中的 http 地址升级为 https 后再核验。
  - 写死的规则检索词已从审查计划中移除；三个官方地址只在搜索无结果、且检索词本身点名该法律时才使用。
- **法律依据**：
  - 审查模型在 `law_refs` 中写明法律全称、条号和要点。系统按法律名称与条号，从已取得的官方页面中截取完整条文作为逐字引文，标注“已对照官方原文”；取不到时标注“模型引用，待核对”。
  - 合同自身的条号不再视为法条主张。未见于合同、依据或所列法条的条号改为提示，并禁止一键采纳，不再清空意见。
  - 复核支持的法律意见计入风险统计。采纳法律修改仍须确认已核对依据。
- **人工修订**：未被复核否定的意见，都可以从建议文本或原段落开始编辑，保存为人工修订，导出前参与组合核验。一键采纳仍须复核支持。
- **状态说明**：状态判定规则不变（“部分完成”从不等于通过），但界面与导出报告按实际原因显示：
  - 有步骤失败：显示“部分完成”，提供重试；
  - 只是部分法律问题未取得官方原文：显示“依据待核对”和“N 个法律问题未取得官方原文”，“重新检索”不会重新调用模型；
  - 只有待人工确认的意见：显示“待确认”，不再出现警告条。
  此前几乎每次真实审查都会显示“部分步骤未完成 / 部分审查未完成”，容易被理解为审查失败。
- **检索诊断**：每个未采用的候选页面都记录原因（HTTP 状态、超时、重定向目标、格式、空页、无对应条文），存入审查的检索记录，便于查日志。
- **其他**：
  - 引文按空白与全半角折叠后定位，保存时仍用原文片段。
  - 合同问答允许引用合同条号，也允许用 `law_refs` 回答法律问题（标注待核对）。
  - 读超时改为 300 秒。截断会单独报错，并以精简要求自动重试一次；限流等待后重试一次。
  - 模型回复里的 `<think>` 片段和前置说明文字不再导致失败。
  - 可用 `LEGAL_YDATA_MAX_TOKENS` 调整输出上限。

## 验证

- **后端**：`python -m pytest -q tests` 共 550 项通过，新增 40 项。其中包括：
  - 大文档最佳情况回归：两种模式都应保留可采纳修订且不超预算。在原实现上，两种模式均失败，可采纳 0 条。
  - 审查组并行执行。
  - 兼容性检查失败时保留修订。
  - 截断后以精简要求重试。
  - 检索词闸门、条文匹配、检索超时与授权撤销。
  - 人工修订经组合核验后导出。
- **前端**：typecheck 通过；lint 0 个错误（仍有原来 KnowledgeGraphView 的 1 条警告）；84 项单元测试通过；生产构建通过。
- **浏览器冒烟**：`scripts/legal_ui_smoke.py` 与 `scripts/research_ui_smoke.py` 均通过。
- **样例回放**（模拟延迟，同一模型桩）：

  | 模式 | 耗时 | 可采纳修订 | 法律意见保留 |
  | --- | --- | --- | --- |
  | 标准审查 | 57 → 14 个时间单位 | 7/13 → 16/16 | 0/6 → 8/8 |
  | 深度审查 | 67 → 18 个时间单位 | 8/18 → 28/28 | 0/10 → 14/14 |

以上均为合成数据与模拟接口，不代表真实模型的审查质量、费用或实际耗时。

- **实网检索诊断**（GitHub Actions，`scripts/legal_retrieval_probe.py`，4 条规划器风格的检索词，每次运行结果不同）：
  - Bing RSS 时好时坏：同一检索词，有时返回法院网、司法部、市场监管总局等官方页面（一次运行中通过搜索取得 2025 年修订的《反不正当竞争法》），有时返回完全无关的页面（新闻、购物、微软帮助页）。
  - 本轮针对此增加：搜索结果中没有任何官方候选时，用核心词重试一次；先筛出官方候选再取前 5 个，无关结果不再占用名额。
  - 四次运行分别有 3、4、3、3 条取得官方原文，其中经搜索取得的只有 0 到 2 条，其余依赖三个写死的官方地址兜底；《反不正当竞争法》不在兜底范围内，搜索失败时就没有原文。
  - `www.npc.gov.cn`（全国人大网，法律全文的主要来源）：搜索能找到，但一个都读不到。诊断确认是 TLS 握手失败（`SSLV3_ALERT_HANDSHAKE_FAILURE`）：该站只接受 Python 默认加密套件列表之外、浏览器仍支持的套件；同一页面走 http 可取得全文。

## 仍需注意

- **检索服务**：Bing RSS 为尽力而为，结果不稳定，建议配置 `TAVILY_API_KEY`（检索范围限定在官方域名白名单）。`scripts/legal_retrieval_probe.py` 用规划器风格的检索词做实网诊断，记录候选来源、准入结果和每个候选的失败原因。
- **全国人大网待决定**：可让检索客户端提供与浏览器相同的加密套件列表（AEAD 前向保密套件优先，其后是 CBC 与 RSA 密钥交换；证书与域名校验、TLS 1.2 下限和官方域名白名单不变，仍不读取明文 http）。该改动放宽了 TLS 配置，已暂缓，由产品负责人决定。
- **部署**：本轮主要是后端改动，需要部署 Fly 后端才生效。当前 Deploy Fly backend 工作流因缺少 `FLY_API_TOKEN` 失败。新前端兼容旧后端（新增字段缺失时隐藏）。
- **尚未实现**：与对方修订稿的多轮比对、Word 批注、缺失条款插入；上市公司专项规则与公司画像。
