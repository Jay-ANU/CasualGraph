# 法务 Agent 前端：C 端体验、视觉与“AI 味”审查及重构

## 范围与方法

基线为 9976783（#10 合并后）。在 Chromium 中用合成合同和模拟 API 走完完整流程：上传、脱敏、确认立场、审查中、结果、采纳、核验、导出、公司规范。分别在 1440、1024、390 像素宽度截图，并与站点首页、研究工作台的现有品牌规范对照，同时逐行阅读了 `LegalDesk.tsx`、`parts.tsx`、`DeskExperience.tsx` 和 `LegalDesk.css`。

这是一次专家走查，不是用户访谈或转化实验。文中没有测量留存、耗时或满意度的变化。

## 一、C 端用户视角的体验问题

| 优先级 | 问题 | 对用户的影响 | 整改 |
| --- | --- | --- | --- |
| 高 | 界面到处是系统视角的保留话术。源码中有 26 处“不代表 / 不等于 / 未核验 / 不替代”一类表述，几乎每个区块都在声明责任边界 | 读起来像在签免责条款，焦虑感上升，反而让人怀疑产品能力 | 只在真正会造成误解的地方保留，每类只说一次，现在共 9 处；其余改成用户语言 |
| 高 | “我方主体”绑定要求用户在下拉框里按段落编号（p2 · …）找段落，再逐字填写原文 | 这是全流程最难的一步，普通用户不理解“段落编号”和“逐字原文” | 从正文中摘出“甲方（采购方）：……”一类候选，一键点选，不预选、不推断；手动方式保留为“找不到？手动指定” |
| 高 | 工程术语直接暴露：p4 段落编号、glm-5.2 模型 ID、“多 Agent 协作审查”、“候选已否定”、“复核状态以本条说明为准”；导出报告里还有 `类别：commercial`、`处理决定：pending` 这样的英文枚举；检索缺口显示 `termination` 这样的规则 ID | 用户看不懂，也显得产品没做完 | 条款名代替段落编号（如“第二条 价款与支付”）；审查方式改为“深度审查 / 标准审查”；报告与检索缺口全部中文化 |
| 高 | 结果页信息架构混乱：导出在最底部（1440 宽下约 3 屏）；“法务 Agent · 检查完成”的状态块夹在意见列表之后；审查进行中时，进度在已出现的意见下面；复核否定的“候选”与真实风险混在同一列表 | 找不到最重要的事：结论是什么、先处理哪条、怎么导出 | 固定顺序：结论 → 待办 → 逐条意见 → 依据与过程 → 追问 → 导出。进度卡置顶；已排除的疑点单独折叠；底部常驻“已处理 x / y · 去导出” |
| 中 | 概览没有结论：只写“有 4 项值得进一步处理”，看不到风险分布；“待你处理 4”和“待核实 2”互相包含，关系不清 | 无法判断“这份合同能不能签” | 标题直接给结论，加风险分布条（高 / 中 / 提示 / 待核实）和“建议先处理 N 项高风险条款”；“待核实”注明“依据或事实不足” |
| 中 | 首屏最显眼的是模型下拉框（glm-5.2 + 刷新按钮），问候语是“今天需要审查哪份合同？” | C 端用户不懂模型；聊天式问候显得“又是一个套壳 AI” | 首屏只留价值主张、上传和隐私承诺；模型选择移到“审查方式”里的次要位置 |
| 中 | 授权分散：上传、脱敏、模型外发、法律依据、手工修改、组合核验、最终确认、导出、追问各有勾选或弹窗 | 用户不知道还差哪一步 | 后端要求的确认一项都没减，但开始审查前加了“开始前需要完成”清单；导出拆成“选择修改 → 核验组合 → 确认”三步，每步显示完成状态 |
| 中 | 手机端顶栏、步骤条、视图切换、提示条几乎占掉 40% 首屏；步骤文字 11px 挤在一行 | 内容区域太小 | 步骤条只显示当前步骤名，与“审查 / 合同正文”切换合并为一行 |
| 低 | 公司规范页的角色复选框与文字上下错位；“COMPANY PLAYBOOK”英文眉题；“让它知道公司的底线”把 AI 拟人化 | 显得粗糙 | 修正布局，改为中文标题“公司规范”和说明 |
| 低 | Max 权限页的口吻是 B 端的“请联系管理员开通” | C 端用户不清楚能得到什么 | 列出 Max 能做什么，保留“返回研究工作台”和“重新检查” |

## 二、UI 设计问题

1. **品牌断裂。** 首页和研究工作台用暖纸色、墨黑、细线，标题用衬线体。法务页却是深藏青侧栏配 #3557AD 标准蓝和冷灰背景，Logo 还是 Georgia 字体的字母“C”，不是正式标志。它看起来像另一家公司的后台模板，直接削弱信任。
2. **没有设计体系。** 一个样式表里有 177 个不同的色值，47 处 `!important`，17 档字号（10–29px），36 种不同的内边距。
3. **层级扁平。** 概览、设置、意见、协作、追问、核验和导出都是“白底、1px 边框、12px 圆角”的卡片，用户分不出哪里是结论、哪里是待办、哪里是附录。
4. **风险等级的视觉很弱。** 高 / 中 / 低只靠 12px 的小色块区分；采纳后也只是边框变绿。
5. **合同阅读体验差。** 每段都挂着“p1 · 第 1 页”；修改对比看起来像普通文字，不像 Word 修订；【脱敏1】显示为普通文字，看不出哪些信息被隐藏了，错过了最能建立信任的视觉。
6. **可读性。** 大量 11–12px 的灰蓝说明文字；按钮文案带括号，例如“对照真实原文（仅有编辑权限可见）”。

## 三、“AI 味”审查

**结论：中度 AI 味，属于结构性的，不是装饰性的。** 页面没有紫色渐变、玻璃拟态或 ✨ 这类元素，但下面这些正是 C 端用户判断“又一个 AI 套壳”的依据：

1. **ChatGPT 式骨架。** 深色左侧栏、“+ 新建审查”、历史列表、底部头像；主区域在代码里就叫 `conversation`、`assistant-response`、`user-message`。
2. **AI 人设和模型外露。** 结果区出现“C 法务 Agent glm-5.2”的助手署名；首页最显眼的位置是模型下拉框；“多 Agent 协作”。
3. **聊天式问候标题。** “今天需要审查哪份合同？”，对应 “What can I help with today?”。
4. **模板化的落地页结构。** 图标眉题 + 大标题 + 副标题 + “01 / 02 / 03”等宽数字；字母间距拉开的英文大写眉题；浅色圆角方块里放线性图标。
5. **防御式文案。** 几乎每段都在写“不代表 / 不等于 / 未核验”，这本身就是 AI 生成文案的典型特征。

整改原则：让界面像**一份被认真批注过的合同**，而不是**一个会聊天的 AI**。具体做法：

- 回到主站品牌：暖纸色、墨黑主按钮、细线、正式 Logo；颜色只用于风险和状态。
- 侧栏改成浅色的“我的合同”文档库；去掉助手署名和聊天结构；用户界面里不再出现“Agent”。
- 合同正文用宋体排版，条款标题加粗，按页分隔；脱敏占位符画成黑色涂抹条，意见段落在页边标注风险色，采纳后变绿。
- 修改对比按 Word 修订习惯呈现：删除为红色删除线，新增为绿色下划线，并附图例。
- 首屏只保留产品标题、上传区和三条隐私要点（见第五节）。

## 四、重构内容

- **结构。** `LegalDesk.tsx` 只保留请求生命周期和状态（原来有一行 JSX 长达 4,907 个字符）。界面拆成 `Sidebar`、`Welcome`、`RedactionStep`、`SetupForm`（含 `ScenarioPicker`、`PartyPicker`）、`ReviewStatus`、`FindingList`、`FindingCard`、`ReviewDetails`、`FollowUp`、`ReleasePanel`、`DocumentPane`、`PolicyEditor`；报告生成移到 `report.ts`；文字规则集中在可测试的 `text.ts`、`labels.ts`。
- **删除死代码。** 未被引用的 `LegalModelPicker.tsx`，以及只包含旧版 `.legal-app` 样式的 `ContractReview.css`。
- **样式。** 一套作用域内的变量（与 `cg-tokens.css` 同源）。色值从 177 个降到 35 个，集中定义为变量；字号从 17 档收敛为 11 档固定阶梯（11–34px）；重置规则用 `:where()` 做成零优先级，`!important` 从 47 处降到 3 处，只留在减少动画的媒体查询里。
- **图标。** 改用站内已有的 `lucide-react`，与首页和研究工作台一致。

## 五、第二轮：文案专业化与结构精简

第一轮上线后的反馈是：标题口语化（如“签字之前，先把合同看明白”“这是什么合同，你是哪一方？”），说明性文字过多，用户并不关心。本轮按以下文案规范重写全部界面文字，并在获准后做了更大的结构调整。

**文案规范**

1. 标题和标签用名词短语：审查设置、我方身份、审查意见、导出。不用问句，也不用“你”，统一称“我方”。
2. 一个元素只说一件事。能从状态看出来的，不再用文字重复（例如候选卡片已显示选中，就不再写“已选择：……”）。
3. 说明文字只保留影响决策或合规必需的内容，每处不超过一行；处理过程、版本号、内部角色等不向用户展示。
4. 免责与授权表述使用规范用语：“审查结果仅供参考，不构成法律意见”“同意……提交所选模型分析”。
5. 按钮用动词短语：采纳修改、保留原文、开始核验、确认修订、导出报告。

**示例**

| 位置 | 第一轮 | 第二轮 |
| --- | --- | --- |
| 首屏标题 | 签字之前，先把合同看明白 | 合同风险审查 |
| 设置标题 | 说明你的立场 / 这是什么合同，你是哪一方？ | 审查设置 / 合同类型、我方身份 |
| 结果标题 | 这份合同有 4 处需要关注 | 审查结果（审查意见 4 · 高风险 1 · 中风险 1 · 待核实 2） |
| 卡片小标题 | 为什么需要关注 / 建议修改为 | 风险说明 / 修改建议 |
| 上传弹窗 | 上传前，确认这份原件的处理方式 | 上传确认（要点三条，完整说明折叠为《原件处理说明》） |

**结构调整**

- 首屏：去掉流程说明和“先说说情况”偏好区（它与审查设置重复），只保留标题、居中的上传区和一行隐私要点。
- 审查设置：改为“标签 / 控件”两栏表单；审查模式改为分段控件；去掉开始前清单，改为按钮旁的一行状态提示。
- 审查结果：结论、风险分布合并为一行统计（衬线数字）；去掉重复的“待你处理 / 已采纳”指标，进度由底部进度条承担。
- 意见卡片：条款定位移入卡片顶部信息行；展开后以“原文 / 风险说明 / 依据 / 修改建议”备忘录式排列；去掉“由某维度提出”和图例等附加信息。
- 审查依据：只保留审查范围、法律检索、交易信息、审查场景四项；协作维度只在审查进行中展示。
- 导出：两张卡片改为一个列表，核验三步收在列表内。

**视觉资产**

由一名独立设计代理先评估哪些位置值得专门设计，再完成绘制。原则是只用产品自身的视觉语言（墨色涂抹条、标红条款、细线纸页），不用机器人、星光、渐变等“AI”意象。共四项，均为内联 SVG 加 CSS 动画，放在 `frontend/src/legal/art/`：

| 资产 | 位置 | 说明 |
| --- | --- | --- |
| `ContractSheet` | 首屏上传区、会员权限页 | 一份双方已脱敏、一处条款被标注的合同；首次出现时依次画出标记，拖入文件时纸页轻微上移 |
| `ReviewingSheet` | “审查中”进度卡 | 代替通用加载圈：逐行“阅读”纸页，3.6 秒循环；排队时静止 |
| `PolicySheet` | 公司规范空状态 | 一支钢笔写下第一条规则 |
| `NoMatchSheet` | 筛选无结果 | 标注位留空（虚线），刻意保持中性，不暗示“没有风险” |

所有资产均为装饰性（`aria-hidden`），在“减少动画”设置下完全静止。评估中放弃的方案包括：审查完成印章（会暗示法律背书）、页角折痕（常见文件图标套路）、纸张纹理和标题下划线（纯装饰）。

## 六、保留的不变量

- 所有接口路径和请求字段不变。上传前授权、脱敏确认、模型外发授权、法律依据确认、手工修改确认、组合核验、最终确认和导出确认一项未减。
- 修改合同类型、角色、主体、补充要求、交易背景、审查方式或模型中的任何一项，都会撤销模型外发授权（`changeSetup` 统一处理）。
- 主体候选只逐字摘自正文，不预选，也不替用户判断立场；后端仍校验引用的原文。
- “没有可采纳的意见不代表没有风险”“AI 辅助审查不构成法律意见”“存储地域为运营方声明”等必要提示保留。
- 键盘和读屏能力保留：跳到工作区链接、移动端抽屉的焦点约束与 inert、原生对话框、`aria-expanded` / `aria-pressed`。修改对比补充了读屏可读的“删除 / 新增”，并修正了 `div` 上不被支持的 `aria-label`。

以上都是合成数据和模拟接口的回归，不证明真实模型的审查质量，也不等于完整的无障碍认证。

## 八、仍建议跟进

1. 主站导航入口仍写作“法务 Agent”。它属于首页范围，本次没有改动，建议统一为“合同审查”。
2. 上传说明全文来自后端版本化文案（`original-upload-v1`），措辞仍偏技术化。修改需要走后端发布流程。
3. 审查报告目前导出为 Markdown。C 端用户更习惯 PDF 或 Word，建议增加格式。
4. 用 5–8 名真实用户做可用性测试，重点验证“主体点选”和“导出三步”。
