# 法务迭代四：四档审查与审查技能框架

基线：`main@089baa0`（迭代三已合并）。

## 需求

- 统一按审查档位设计，不再区分单 Agent 与多 Agent：极速、快速、标准、深度。极速档按普通大模型产品的方式直接作答。
- 为这个 Agent 产品搭建技能（skill）机制；评估 `vivy-yi/Greater-China-Legal` 能否接入，并从 GitHub 寻找可用技能。

## 四档审查

四档共用 `legal/review_v2.py` 的同一条流水线，只在“跑哪些步骤”上不同。

| 档位 | 运行的步骤 | 关键路径 | 一键采纳 |
| --- | --- | --- | --- |
| 极速 `ultra_fast` | 各审查组并行，要求每组只报告最重要的问题 | 1 次模型调用 | 不可；意见标注“未复核”，可保存为人工修订 |
| 快速 `fast` | 审查组并行，每组完成即独立复核；同段落不同修改自动判为冲突 | 2 次 | 复核支持即可 |
| 标准 `standard` | 快速档加上模型规划的法规检索和全文兼容性检查 | 约 3 次 | 同迭代三 |
| 深度 `deep` | 法律、商业、公司规范专项 Agent，加复核与全文协调 | 约 3 次（调用更多） | 同迭代三 |

- 请求字段 `review_tier`；旧字段 `review_mode` 仍可用（`multi_agent` 对应深度，`standard` 对应标准）。已创建的审查保持原模式。
- 各档位不做的步骤只在每条意见上标注，不会让审查变成“部分完成”：
  - 极速：`verification_status=skipped`，风险按严重程度计数；
  - 快速：未做交叉核对，标注“本档位不做全文交叉核对”。
- 不变量：
  - 极速档意见不能一键采纳，只能在人工确认后保存为人工修订；
  - 导出前仍须组合核验并由人工确认；
  - 采纳法律修改仍须确认已核对依据。
- 前端通过 `/legal/capabilities` 的 `review_tiers` 判断后端能力。旧后端只显示标准与深度，因此前端可以先于后端上线。默认档位由深度改为标准。
- 进度卡只显示该档位实际运行的步骤：
  - 极速：读取合同 → 分项审查；
  - 快速：读取合同 → 分项审查 → 逐项复核。

## 审查技能框架

技能是经维护的审查方法与检查清单，用来提示检查要点，不是法律依据。法律依据仍以 `law_refs` 和官方原文核对为准。

- **格式**：`legal/skills/<id>/SKILL.md`。YAML 头包含：
  - `id`、`name`、`description`、`version`；
  - `status`：`active` 或 `draft`；
  - `applies_to`：`always`、`scenarios`、`keywords`、`min_keyword_hits`；
  - 可选的 `tiers`；
  - `source`：来源、仓库、提交、路径、许可。

  正文是审查指引（每个不超过 6000 字）。
- **加载**：`legal/skill_registry.py` 负责校验。格式错误、缺许可、id 与目录不一致的技能会被跳过并记日志，不会影响审查。
- **选取**：确定性规则，按“通用、合同场景、合同原文关键词”打分，每次最多 4 个。各档位有字数预算：极速 4000、快速 6000、标准 9000、深度 12000。每个技能附带选中理由，例如“合同涉及：人工智能、患者”。
- **使用位置**：
  - 审查调用：作为 `skills` 字段；提示词写明它不是依据，冲突时以合同原文、规则和公司规范为准。
  - 合同问答：同样作为 `skills` 提供。
  - 复核调用：不使用，复核只对照合同与来源。
- **留痕**：审查创建时把选中的技能快照（id、版本、内容哈希、理由、正文）写入审查记录；断点续跑使用同一快照。
  - 接口 `skills` 只返回来源信息，不返回正文。
  - `GET /legal/skills` 返回启用中的技能目录。
  - 页面“审查依据 → 审查技能”和导出报告列出所用技能。
- **引入外部技能**：`scripts/import_legal_skill.py`。
  - 只接受宽松许可（Apache-2.0、MIT、BSD、CC-BY-4.0），并记录仓库、完整提交 SHA 和路径。
  - 导入结果为 `draft`，且没有 `applies_to`，不会被任何审查使用。
  - 由律师核对、压缩为审查指引、设置适用条件后，再改为 `active`。

### 首批技能（均为 active，尚未经执业律师复核）

| id | 名称 | 适用条件 | 来源 |
| --- | --- | --- | --- |
| `review-method` | 合同审查方法 | 所有审查 | 改编自 anthropics/claude-for-legal 的审查流程（Apache-2.0，许可证文本见 `legal/skills/LICENSES/`） |
| `service-tech-contracts` | 服务与技术类合同 | 服务、技术服务、技术开发、软件开发、软件许可、SaaS、运维场景，或原文出现两个以上相关词 | 自研 |
| `personal-information` | 个人信息与敏感数据 | SaaS 场景，或原文涉及个人信息、患者、病历等 | 自研 |
| `ai-services` | 人工智能服务 | 原文涉及人工智能、算法、模型等 | 自研 |
| `listed-company` | 上市公司合规视角 | 原文涉及上市公司、关联交易、信息披露等 | 自研 |
| `cross-border` | 涉港澳台及跨境合同 | 原文涉及香港、澳门、台湾、境外、外汇等 | 自研 |

各技能只引用有把握的条文，版本不确定的写成“核对现行规定”。对用户提供的口腔 AI 顾问合同，会选中审查方法、服务与技术类合同、人工智能服务、个人信息四个技能，四档预算内都放得下。

## 外部技能评估

### vivy-yi/Greater-China-Legal（提交 `fccdf09`）

- **规模与来源**：574 个 SKILL.md。仓库每月从 `anthropics/claude-for-legal` 同步，市场清单的所有者仍写作 Anthropic。多数技能按 Claude Code 交互式工作流编写（斜杠命令、配置文件、外部数据源标注），不能直接用于本产品的结构化审查流水线。
- **许可**：README 声明 Apache 2.0，但仓库没有 LICENSE 文件。在补齐之前不复制其内容。
- **抽查发现的实质错误**：
  - `LEGAL_FRAMES/cn-mainland.md`：
    - 2023 年修订的公司法生效日期写为 2024 年 1 月 1 日，实为 2024 年 7 月 1 日。
    - “合同自由原则”标为民法典第 4 条（第 4 条是平等原则，自愿原则在第 5 条）。
    - “有偿等价原则（§646-第463条）”等条号与内容无对应关系。
    - 民事诉讼举证责任仍按旧条号（§64–66）。
    - 仲裁法仍列为 2017 年修正。
  - `contract-review/civil-code-checker`：
    - 把“无权处分的买卖合同”列为“效力待定（民法典第597条）”。第 597 条规定的是出卖人未取得处分权、致使所有权不能转移时，买受人可以解除合同并请求其承担违约责任，买卖合同并不因此效力待定。
    - “4 倍 LPR（2024 年约 14.2%）”：14.2% 对应一年期 LPR 3.55%，是 2023 年的水平；2024 年一年期 LPR 已不高于 3.45%。
- **结论**：不接入。如作者补齐 LICENSE，可按具体技能用导入脚本引入为草稿，经律师更正后再启用。

### anthropics/claude-for-legal（提交 `4a6c651`）

- Apache-2.0（有 LICENSE），151 个技能，以美国法为主，同样面向 Claude Code 交互式工作流。
- 采用了其合同审查流程的思路：先定位交易、先查致命条款、逐项对照、写出可直接替换的文本、按规则升级。按中国大陆实务重写为 `review-method`，注明来源、提交和许可。
